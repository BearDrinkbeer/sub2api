# Windows AD 历史部署升级方案

适用：从旧 `codex-windows-ad-login` 部署，升级到基于新版 main 的 AD 版本。
采用“备份恢复预演 + 短暂停写切换”，不承诺零停机。
本说明不是已完成的生产验证；生产数据库和域控必须在部署环境预演。

## 升级前提

- 固定旧镜像和新镜像的 tag/digest，保留可离线导入的旧镜像，不使用 `latest`。
- 这次只升级应用，不同时升级 PostgreSQL/Redis 大版本，不新建空库替换原库。
- 保存部署目录、Compose 文件、`.env`、实际挂载配置和 `/app/data`，保留原 JWT、TOTP 和其他加密密钥。
- 保留 AD 的 Base DN、唯一 ID 属性及身份数据；不要重置账户或重新导入域用户。
  身份映射沿用 `windows_ad + Base DN + objectGUID`，已有用户 ID、余额、API Key、订阅和历史日志应继续关联原账户。
- 离线部署关闭所有公网验证码及不用的外部登录，并确认未配置 `turnstile.required=true`。内网放通应用到域控的 LDAP/LDAPS；使用 LDAPS/StartTLS 时保留受信任的内部 CA，LDAP URL 中的主机名/IP 必须匹配证书。
- AD 用户通过域认证后，不受公开注册开关、邀请码和注册邮箱后缀白名单限制；其他登录方式不变。AD 的准入范围由搜索路径/过滤器控制，应用内禁用用户、后台模式和已启用的二次验证仍生效。
- 按内网额度不敏感的使用要求，保留现有首次绑定默认授权逻辑。旧版缺少 AD 授权记录时，升级后可能补发一次默认额度/订阅；不自动回写授权历史或调整现有余额。

## 数据库兼容处理

旧部署的 136 AD 迁移与 main 的 136 钉钉迁移是不同文件，迁移器按完整文件名识别，不能仅看数字编号。
main 原版钉钉迁移会重新建立不含 `windows_ad` 的约束，有 AD 历史数据时会中途失败，不能只在末尾补一个 AD 迁移。

本分支针对该升级路径：

- 136 钉钉迁移和 140 默认授权迁移同时接受钉钉及 AD，保留已有 AD 行。
- 校验和兼容只允许这两条迁移的已知原版及本分支版本，不关闭全局校验，不要求手改 `schema_migrations`。
- 新增 247 迁移，统一用户来源、身份、身份渠道、待完成认证、默认授权记录五张表的约束。
- 补齐 Ent 和仓库层来源校验，后续新 AD 用户正确保存 `windows_ad`。
- 不批量重写旧用户来源，避免把原有邮箱账户误改为 AD 来源；旧版产生的 `email` 来源不会因此丢失 AD 身份绑定。

## 第一步：隔离预演

1. 在 GitHub 完成单元测试、集成测试和镜像构建，记录对应提交及镜像 digest。
2. 对生产 PostgreSQL 做完整逻辑备份，并确认备份可恢复。以下是 Linux 部署机的命令示例，服务名按实际 Compose 配置调整：

   ```sh
   docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > sub2api-pre-upgrade.dump
   ```

3. 在独立数据库、独立 Redis 和独立应用数据目录恢复副本。隔离邮件、支付通知和所有生产流量，防止预演环境执行生产任务。
4. 导入 GitHub 构建的离线镜像，只启动一个新应用实例，让内置迁移器执行迁移。大型历史库建索引和数据回填耗时可能较长，以预演记录为准。
5. 查看启动迁移日志，确认没有 checksum mismatch、约束失败或超时。不要通过清空迁移记录、重建业务表来绕过错误。
6. 核对升级前后的用户数、用户 ID、API Key 数、余额合计、有效订阅、订单和使用记录。新主线可能包含数据转换，不能仅用总表数判断成功。
7. 验证原管理员登录、已绑定 AD 用户登录、新 AD 用户首次登录、禁用用户拒绝登录；确认同一 AD 用户不重复建号，升级后的默认额度/订阅符合内网使用要求。
8. 验证现有 API Key 请求、额度扣费、历史用量查询。新主线的其他业务变化也必须在副本上验收。

## 第二步：生产切换

1. 进入维护窗口，停止入口流量并等待在途请求、计费落库结束；停止所有旧应用实例和其他写入同库的任务。
2. 停写后重新制作 PostgreSQL 最终备份、Redis 一致性备份以及应用配置/密钥快照，记录恢复点。不要执行 `docker compose down -v`。
3. 只替换应用镜像，保持现有数据库、Redis、卷挂载和密钥不变。先启动一个新实例，避免新旧应用同时操作迁移中的数据库。
4. 确认迁移完成，复核核心数据和管理员/AD 登录，再验证 API Key、扣费、订阅和历史记录。确认通过后开放流量并恢复其他实例。
5. 保留备份和旧镜像至观察期结束；迁移失败时先停新应用，再按回滚步骤处理，不要重复盲目重启。

## 第三步：回滚

- 新版迁移可能改变数据或删改字段，不能假定只切回旧镜像就能恢复。
- 开放流量前失败：停止新应用，恢复同一停写恢复点的 PostgreSQL、Redis、应用配置及密钥，再启动旧镜像。
- 开放流量后失败：先停写，备份故障时现状和日志，核对新产生的订单、充值、扣费等增量，再决定恢复或向前修复。
  直接恢复旧备份会丢失切换后的写入，不能自动执行。
- 不把预演库的业务数据覆盖回生产库；预演成功后，生产仍使用最终停写备份对应的原库执行同一版本迁移。

## GitHub 验证范围

仓库 CI 负责代码、单元测试、集成测试、AD 专项前端用例及内嵌前端的 Linux 服务端构建，产物保留七天。
生产镜像通过 Release 工作流构建；其 `workflow_dispatch` 支持选择该分支并启用 `dry_run`，构建产物而不正式发布。
GitHub 的空库集成测试不能替代真实历史库恢复预演；实际迁移耗时、磁盘容量和域控连通性需要在内网副本上确认。
